# S07 T09 正式性能与稳定性验证

## 验收口径

T09 的四项预算来自批准方案 §5。使用正式 WSGI 配置，在真实 PostgreSQL、Redis、Worker、唯一 Beat 与同源 HTTP 上运行。两轮热测分别采用 R1 → R2 → R3 → R4 和反向次序。五个普通用户各用真实 Session 和独立连接池，每个形状先预热 10 次，再采样 100 次，共 500 个样本。P95 是按耗时排序后的第 475 个值。单次耗时从开始发送到读取完整响应体。每条样本保留状态、响应字节、内容校验、会话起止和重叠区间。R2 的首页与后继页分层报告。B 补测沿用相同产品和查询，每形状五名用户各跑 10 次。[批准方案](../plans/S07_IMPLEMENTATION_PLAN.md)

## 重建与运行

使用候选 Git 提交的干净副本或经 manifest 校验的交付包，在锁定依赖准备完成且其他验收空闲时运行。`compose.yaml` 提供基础服务，`compose.offline.yaml` 提供随软件交付的正式 Gunicorn 配置，最后由 `scripts/s07_isolation.yaml` 登记本轮资源。Guard 生成空数据库、专属卷、Redis 和 Beat 锁文件，核对归属、双内网路由、数据库与 Broker 标记后再迁移。运行器为每轮固定一个空闲回环端口，重启时保留五个 Session 的原同源地址。应用退出后清理本轮资源。运行器记录配置文件、锁、迁移、源码摘要、独立构建镜像与实际 PID 1 argv。Gunicorn 配置固定为 `1 worker / gthread / 8 threads`。[启动与运维](../operations/S07.md)

```sh
uv sync --locked --offline
.venv/bin/python -B scripts/verify_s07.py performance heat
.venv/bin/python -B scripts/verify_s07.py performance reverse
.venv/bin/python -B scripts/verify_s07.py performance diagnose
.venv/bin/python -B scripts/verify_s07_host.py performance
```

`heat` 先跑正序，再用同一组 Session 和数据连续测量 20 分钟，然后做 PG/Web 冷态重启。`reverse` 另建空实例，按逆序执行正式热测。`diagnose` 独立采集同产品年窗并发的等待，以及四形状的等价 Django Session 与 `EXPLAIN (ANALYZE, BUFFERS, FORMAT JSON)`。每轮原始收据在 `tmp/s07-evidence/<run>/performance/`，环境与清理在 `environment.json` 或宿主 `V01/result.json`。正式运维步骤见启动手册。五个 Session 的凭据仅在进程内使用。样本保留合成用户标识和内容校验结果。[A 运行器](../../scripts/s07_t09.py) · [B 运行器](../../scripts/s07_performance_host.py)

## 数据规模与独立对账

合成源 `s07.fixture` 建立 F-C 和 F-S 各一个产品。固定种子 `707`，从 `2024-01-01T00:00:00Z` 开始，城市侧 5 城合计 20 条对象指标序列，站点侧 20 站址合计 80 条序列，每条按清单建立 10,000 小时键。实际为 200,000 城市键和 800,000 站址键。独立 SQL 检查同数唯一小时键、当前修订和贡献收据。每类分属 835 个有界批次。热点 F-C 使用 UTC 历表，CO 单位为 mg/m³，按小时标签查询。对比窗内 6 个无键格移至主期外，另有 4 个有键缺值和 3 个有效峰值。造数使用模板的规范化与修订服务，批量写入已守卫的空库，再执行 `ANALYZE`。各表 heap/index/total、WAL、临时空间和按维度分项在 `manifest.json`。[造数](../../scripts/s07_performance_seed.py) · [独立 SQL 核对](../../scripts/s07_performance_oracle.py)

| 请求 | 对账结果 |
|---|---|
| R1 24 小时明细 | 24 个连续有效键，核对时间、时间窗、单位和浓度 |
| R2 100 行分页 | 第一页与后继页各 100 行，排序和游标均核对 |

## R4 瓶颈与回归

首次预算失败时相同授权窗口的五个请求叠加了年度分桶和异常候选四分位成本。在 B 的独立 SQL 诊断中，旧月桶排序耗时 270.205 ms，落盘 76,912 KiB，旧候选查询耗时 1,437.776 ms，城市键顺序扫描滤掉 175,674 行。修复将排名所需的窄行先物化、每列四分位只计算一次，并在连接条件中加等价的维度与小时范围谓词。修复后月桶 48.520 ms，临时块为零，候选查询 42.218 ms。PG 通过 `cityobservation_instant` 复合索引只读取所选窗内的 8,781 个键。20 条 SQL 在等价 Django Session 请求内共用 300.945 ms，总请求用 323.682 ms，完整五会话测量按 HTTP 端单列。调优保留源与产品行锁，撤权、版本和拒绝时零字节的实际回归见上文票据。源代码提交 `9be66a1`。[年度统计](../../backend/observations/research_statistics.py) · [选数](../../backend/observations/analysis_query.py)
