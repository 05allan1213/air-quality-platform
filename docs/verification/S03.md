### F01　给已知未发送的任务保留 HTTP 尝试

在原版 `reserve → execute → record_failure → retry_due` 上，`budget_exhausted` 进入普通重试。PG 复现中，第一个任务占用额度，第二个任务留下三个不同 UUID，`attempt=1/2/3` 均为 `failed/unsent`、零预留，第三条的 `next_retry_at` 为空。该反例使用 F 传输替身并推进扫描时刻，原始记录在 `tmp/s03-f01-f02/original-f01.json`。

`admission.check_budget` 在来源锁内按 PG 预留计算滚动限额、最小间隔和并发占用各自的首个可用时间。`budget` 取来源与所有适用产品许可中的最晚值，遇到更早的许可生效/到期或 latest 窗截止时先复核。`reserve` 把等待落在当前 Run，释放窗口 owner，保持 `pending/unsent/budget_exhausted`、原 UUID 和 `attempt`。Beat 扫描到期项，经 `retry_due` 复核 Job、发起者、执行者、来源许可、暂停、窗口及回溯性，才安排投递。认领及预留仍按 Source → Product → Job → Window → Run 顺序复核。并发占用提前释放时可在提交后提前唤醒，通知失败仍有原 PG 计时器。`possible` 访问保守计费，实际瞬态失败沿原来的有界退避链处理。

V16 通过同源 C、L 两个 Job 竞争每 60 秒 1 次的额度。`worker-b-1` 先接收 C，`worker-1` 首次接收 L。L 的 Run `ceafd532-3a81-4a6e-ac7f-1dc47c8cc8e3` 在等待时无预留、无前驱，`attempt=1`。按首份预留算得下次检查恰为 60 秒。按 PG 时间限定日志后，在到期前实录 2 次已完成的 Beat 扫描，当时 C 有 1 份预留、L 有 0 次 HTTP。恢复后 L 沿用原 UUID 和 `attempt=1`，以 `finished/responded` 结束。两项任务共 2 份 PG 预留，两次实际内部 HTTP（C POST、L GET），两次预留相隔 **61.375581 秒**。本例的恢复使用自然流逝的时间。另一个真实 loopback HTTP 503 反例加速退避并移动测试预留时刻，第三次尝试先被本地额度拦下，随后真正发出第 3 个请求，最终恰好三份预留、三个 503、没有生成第四次尝试。

新增迁移 `collection.0006_reconcile_legacy_quota` 将旧的、确认无预留的配额拒绝从自动后继的尝试序号中扣除，只为符合恢复条件且尚未处置的末端安排检查。该单向数据校正保留 UUID、前驱及真实请求证据。PG 用两条旧账本验证全未发送链、含末次真实失败的链。升级时需暂停新触发、停止旧 Worker 和 Beat，迁移后启动新代码。操作顺序见 [README](../../README.md)。
