## 关键决定与故障复测

- 竞态测试只在一次性 PG 库安装 `BEFORE UPDATE OF dispatch FOR EACH STATEMENT` 触发器，使用 advisory lock 挂起真实 Web 的投递更新。观察到 Web 正在等待、HTTP 尚未返回、真实 Worker 已经提交 `succeeded/pending` 与 PK 2。释放锁后 HTTP 202 返回同一 UUID，逐字段比较只变更为 `dispatch=sent`。每例移除触发器。
- Web 的发布调用和 Celery 配置均关闭自动发布重试。Kombu Redis transport 的懒连接使用 `max_retries=0`。连接池等待、连接和单次 socket I/O 均设 1 秒，关闭 `retry_on_timeout`。5 秒证据指本机真实停 Redis 场景的端到端耗时。Worker 保留自己的重连机制。
- 为避免给应用授予 PG 超级用户或建库权，Compose 比计划示例多一项独立的 `POSTGRES_ADMIN_PASSWORD`。仅自有验收项目内的 `s01_pytest` 临时角色可建测试库。PG 探活使用 TCP，避开初始化期间的临时 socket 实例。
- 开发过程曾中止一次缓慢的首次依赖下载，随后通过宿主已有代理预热相同锁文件的 BuildKit 包缓存。另一轮首次走到 V04 限速复验时，运行器沿用旧回环端口导致 ready 超时，已记录为 FAIL（`s01vdef6848413c2`）。单独复现端口由 52816 变为 52817 后，运行器改为重启后查询实际端口，两轮最终结果均已覆盖此路径。
- 内部代码及验证审查还补上许可锁等待期间撤销角色的真 PG 回归、合法 JSON 填充至 16385 字节的拒绝、跨进程数据库失败日志脱敏和清理抛错时写失败收据的处理。两轮均核对了 Worker 故障点命中、回滚及日志。首次额外故障注入试跑（`s01vc0e223761973`）发现应用角色没有测试序列的 USAGE，断言捕获到故障标记未命中。修正仅给该项目的一次性标记序列授予 USAGE，之后才以 `is_called=true` 证明注入位置。清理本身的失败注入为 NOT RUN，实际正常清理成功。
