# S06 操作手册｜质量治理、数据处置与运行管理

S06 封版裁决、验证基线、未验证范围和 S07 复核事项见 [S06 正式验收与实施验证](../verification/S06.md)。

## 隔离运行与升级

S06 演练只使用 F 和任务自有的可销毁资源。共享 Web 和 PostgreSQL 含真实 CNEMC 数据及未完成处置待办。禁止在共享环境迁移、启动 Worker 或 Beat、运行处置扫描、注入故障以及备份恢复。禁止新发 CNEMC 请求。使用 H 前须重新核对本次操作、受众、范围和期限的授权。

在仓库根目录运行。需要项目 `.venv`、本机 Docker Unix socket、运行器指定摘要的 PostgreSQL 16 Alpine 镜像和 Linux `bubblewrap`。Redis、Worker、Beat 演练需本机 `redis-server`，恢复演练还用 `/usr/bin/openssl`。入口冻结当前实际源码快照，创建带随机运行标记的 socket-only PG，业务进程进入私有网络命名空间。每次运行都会重做守卫，`CNEMC_MODE=off`。

```sh
env PYTHONDONTWRITEBYTECODE=1 .venv/bin/python scripts/verify_s06.py guard
```

检查控制台给出的 `tmp/s06-evidence/<run>/V01/result.json`。仅在 `guard` 和 `result` 都为 `PASS`、`cleanup` 为 `true`、`remaining_containers` 为 `0` 时继续。失败时按同一收据定位守卫原因，核对镜像、命名空间、标记、Unix socket 或残留资源的归属。仅处理出自本次运行且已经核对归属的资源。

| 验证入口 | 复验内容 | 同次收据 |
|---|---|---|
| `verify_s06.py pytest` | 真 PostgreSQL 测试。实际参数须为仓库测试路径或节点。省略选择器运行完整套件 | `pytest.json` |
| `verify_s06.py services` | 回环 HTTP、独立 Redis、Worker、单 Beat、健康与文件处置故障 | `runtime.json` |
| `verify_s06.py collection` | 隔离的合成采集链和故障诊断 | `runtime.json` |
| `verify_s06.py upgrade` | 从冻结的 S05 Git 基线构造旧账本，在同一任务自有数据库上前向迁移和对账 | `upgrade.json` |
| `s06_restore_verify.py` | 备份与恢复专项，另建目标数据库及角色和包外保管目录 | `pytest.json` |

表中每条入口都通过 `env PYTHONDONTWRITEBYTECODE=1 .venv/bin/python scripts/<入口>` 执行。例如复验账号、采集控制和质量接口可运行 `env PYTHONDONTWRITEBYTECODE=1 .venv/bin/python scripts/verify_s06.py pytest tests/test_s06_accounts.py tests/test_s06_collection.py tests/test_s06_quality.py tests/test_s06_catalog.py`。备份专项测试依赖该专用恢复入口，普通 pytest 中的跳过不能计为通过。运行结束核对守卫和清理收据。`upgrade` 以 `be6681298a28220ac97136087a4bdf316799c93d` 为旧码基线并验证指纹。迁移叶节点和升级结果以该次收据为准。涉及账号会话代次及审计、Job/Run/Source/Product 控制版本、质量和目录版本、留存边界、受控存储与备份元数据。标记 `legacy_boundary_review` 的旧数据没有足够的连续性证据，按待复核处置，不以人工扫库、重授或修改标志解除。

## 会话与账号管理

每个角色使用单独的客户端 Cookie jar。下表路径以 `/api/v1/` 为基准，测试账号及密码由对应 F 用例在隔离环境生成。

1. `GET auth/csrf/`，保存响应 Cookie 和 `csrf_token`。用同一 Cookie jar 和 `X-CSRFToken` 调用 `POST auth/login/`，JSON 只含 `username` 和 `password`。
2. 登录后再次获取 `auth/csrf/`，后续 POST 使用该 Session 的新 Token、同源地址和 `Content-Type: application/json`。`GET me/` 检查当前身份。退出调用带 CSRF 的 `POST auth/logout/`，成功为 `204`。
3. 账号管理员先 `GET admin/accounts/<account_id>/actions/`，读取 `active`、`version`。向同一路径 POST `action`、`request_id`、`reason_code: "account_review"`、`expected_version`。每次新意图生成规范小写 UUID，`expected_version` 使用 GET 返回的整数。成功响应为 `200`，记录 `action_id`、`active`、`version`。

| 账号动作 | 附加参数与规则 |
|---|---|
| `enable`、`disable` | 无附加参数。停用推进 Session 代次。再次启用后，未使用过的停用前 Cookie 也须重新登录 |
| `grant`、`revoke` | `permission` 为服务端允许的具名权限。普通管理员不能授撤自己缺少的权限 |
| `grant_role`、`revoke_role` | `role` 支持 `collection_operator`（`observations.run_collection`）和 `quality_reviewer`（`observations.review_observation`） |

受限 `/admin/` 入口要求 staff 和 `accounts.manage_accounts`。账号变更与 JSON API 共用服务，禁用自我变更、普通管理员管理同级及更高权限管理员、通用组提权、改密以及批量删除。首次超级管理员初始化由受控主机运维单独完成。账号启禁、授权变化和业务写入回执在同事务提交。检查撤权是否生效时保留受影响账号的原 Session 发起下一条请求。原 Session 的私有资源仍按 owner 和合成域核对，管理员也须通过来源用途检查。

| 职责 | 具名权限 |
|---|---|
| 账号管理 | `accounts.manage_accounts` |
| 采集 | `observations.run_collection` 发起运行，`observations.manage_collection` 执行控制 |
| 质量与目录 | `observations.review_observation` 审阅，`accounts.adjudicate_quality` 裁决，`accounts.manage_catalog` 治理站址 |
| 权利、处置与保管 | `observations.manage_grants` |
| 分段备份与恢复 | `accounts.manage_backups`、`accounts.restore_backup` 各按动作核验 |
| 运行诊断 | `accounts.diagnose_operations`，查看具体窗口还需该窗口适用的权限和用途 |

## 采集控制与失败定位

在 F 场景先 GET `admin/collection-jobs/<id>/`，读取 `targets.job`、`targets.source`、`targets.product` 的 `control_version` 和状态。Run 在 `GET admin/collection-runs/<uuid>/` 查 `target`。下列新协议 POST 统一提交 `action`、`request_id`、`reason_code`、`expected_version`。理由白名单为 `operator_pause`、`operator_resume`、`operator_recovery`、`incident_review`。目标版本以对应对象的 GET 为准。

| `action` | POST 路径和锁内目标 | 处理 |
|---|---|---|
| `pause` | `admin/collection-jobs/<id>/` 的 Job | 暂停单 Job。旧请求 `{"action":"pause"}` 仍可紧急使用，审计标记旧协议 |
| `resume` | 同一路径的 Job | 复核采集准入和执行账号 |
| `resume_source` | 同一路径引用的 Source | 引用同 Source 的 Job 共用版本。复核暂停状态和冷却期 |
| `resume_product` | 同一路径引用的 Product | 引用同 Product 的 Job 共用版本。复核暂停状态和执行资格 |
| `redeliver` | `admin/collection-runs/<uuid>/` 的 Run | 只重投原本 `pending/unsent/manual`、没有 owner 的 Run，保留原窗口 |

除 `pause` 外只给 `action` 的旧请求返回 `400 invalid_request`。Job 成功为 `200` 和 `{job, enabled, reason}`，重投成功为 `202` 和 `{run_id, window_id}`。收到 `409` 时以当前诊断重新确认实际目标和动作。相同请求号用于重试原参数，改目标、理由或版本应新建请求号。不能以批量开关或直接改库绕开自动暂停和人工控制共用的版本。

1. 从失败 Run 的 GET 或 `admin/collection-windows/<id>/` 回查窗口状态、已获准的 Run/Item、失败码和覆盖。队列提交成功只证明投递状态，窗口结果和观察覆盖从 PG 账本确认。Run 的 `quality_issues` 只显示当前获准审阅的事件。
2. 按 `product` 和 `run` 或 `window` 查 `GET admin/quality-issues/`，F 必须加 `scope=synthetic`。可按 `status=open|in_review|resolved` 和 `before` 分页。查事件详情确认失败阶段、候选和资格。
3. 可见质量明细另需当前范围的 `quality_detail` 留存和审阅授权。仅有 `collection_ledger` 时保留获准的 Run 状态、错误码和子项结果，隐藏事件及字段诊断。只撤审阅权时库中仍可保留明细。撤回留存权后以待办对账事件、字段诊断和获准运行账。
4. 仅在 Run 确实可重投时使用 `redeliver`。配额等待看窗口的等待与时间诊断，冷却等待看 Source 状态。来源、执行账号及用途还不满足时保持暂停。不存在清单或授权收窄时，仅凭已获准投影定位，避免根据隐藏记录补写完成状态。

## 裁决、站址与下游失效

先 `GET admin/quality-issues/<id>/`，取得 `event_version` 和 `evidence`。写 `POST admin/quality-issues/<id>/actions/`，提交 `action`、`request_id`、`reason_code`、`expected_version`（该 `event_version`）和 `evidence_ref`。用下表配对理由和引用。`200` 返回 `action_id`、`status` 和新的 `event_version`。

| 动作 | `reason_code` | `evidence_ref` |
|---|---|---|
| `claim` | `claim_review` | `null` |
| `hold` | `retain_isolation` | `null` |
| `close` | `review_complete` | `null` |
| `correct_source` | `verified_correction` | `evidence.correct_source` |
| `correct_mapping` | `registered_mapping` | `evidence.correct_mapping` |

工单结案可保留观测隔离。来源订正须有服务端核准契约和覆盖全部候选的证据。正式来源尚无可用排序依据时保留争议。本站映射须能合法复查原字段并适用已登记规则。预审跨键目标时，详情 GET 加 `mapping_target=<F 目标对象码>` 取得绑定目标的引用。两端须具备所需用途。映射成功后核对旧、新键及 `MappingLink`，目标冲突时复核双方隔离。提交 `409` 后重取详情、核对候选集合、当前修订和可信水位再裁决。纯迟到证据、同值推进水位和真正改变内容须分别对账。

站址操作用 `GET admin/stations/<station_id>/changes/` 预审。传 `product`、`action`、`identifier`（已登记的代码标识 ID）、`at`（带时区的生效时刻）、`target`。同一路径 POST 使用质量命令信封，`expected_version` 和 `evidence_ref` 取预审结果。`200` 返回 `action_id`、`status` 和新的 `version`。

| `action` | `target` | `reason_code` |
|---|---|---|
| `rename` | F 新名称 | `documented_rename` |
| `relocate` | 同源已登记城市 ID | `documented_relocation` |
| `reuse_code` | 同源已登记的目标站址 ID | `documented_code_reuse` |

提交后按有效区间查询目录，核对旧时槽、旧站址 FK 和收藏的原身份。跨越边界返回 `mapping_review_required` 时先复核旧观测映射。未登记的正式来源目录证据保持关闭。

裁决或目录变更提交前后分别获取查询、统计和下钻结果。用受影响范围及不相交范围各做一份对照，跨键映射取两端，填补缺槽也计入影响。统计内容版本和精确输入版本分别比较，同值推进可信水位可能保留统计版本并使旧下钻及导出失效。保存查询属于用户私有意图，运行时按当前许可和输入重算。下载访问 `GET me/exports/<uuid>/download/`，以服务端最终核权事务的提交顺序判定。旧精确输入返回 `409 input_changed`，回到现行查询重新领票。在核权先提交的次序下可返回当次完整 CSV，撤权先提交或核权事务回滚时没有 CSV 字节。跨 owner 访问按私有接口协议拒绝。查询及票据创建方法见 [S05 操作手册](S05.md)。

管理动作退回后按响应代码处理。

| 响应 | 操作 |
|---|---|
| `400 invalid_request` | 按动作核对字段白名单、UUID 格式和整数版本 |
| `403 csrf_failed`、`not_authenticated` | 用当事 Session 重新获取 CSRF，检查账号启停和 Cookie 是否有效 |
| `403 permission_denied`、`use_denied` | 核对具名权限及当前来源用途、字段、受众和范围 |
| `404 not_found` | 核对资源 ID 和所属 Session 或数据域 |
| `409 precondition_conflict`、`input_changed` | 重读 GET 快照，核对版本、证据或输入后发起新动作 |
| `409 request_conflict` | 对照原请求参数。用原 UUID 重放相同请求时，仍须通过当前权限和适用的证据检查。新动作使用新 UUID |

## 分服务健康

匿名 `GET /health/ready/` 输出最小 Web/PG 状态，PG 不可用时返回 `503`。具名 `GET /api/v1/admin/operations/health/` 另外给出 Redis `PING`、Worker 心跳、采集队列订阅和最近成功消费，以及 Beat 实际 tick。每个组件分别看 `state`、`observed_at`、`valid_until`、`evidence_kind`、`reason_code`。默认 Worker 和 Beat 证据有效期为 30 秒，隔离运行器缩至 3 秒。缺失或过期为 `unknown`。Redis 在线时仍须查看 Worker 与 Beat 各自证据。

心跳有效且 `queue_readiness.state` 为 `unavailable`、原因 `queue_not_subscribed` 时，对照路由检查 Worker 的 `-Q` 配置。恢复订阅后，通过下一次实际消费和对应 Run 判断积压是否消退。

故障排查时按需加 `window=<id>`，还可传 `object_code`、`indicator`。检查获准页面内的未启动已发送、投递未确认和配额等待数、等待年龄及覆盖。`truncated` 表示有后续页面。需要解释错过的时槽时结合 Run、质量事件及窗口结果查询。合法旧值可按原查询契约读取，明确其观测时间。故障期间的明确历史窗仍保留缺口，健康和业务 GET 均无需投递采集任务。

## 权利撤回与待核销

权利管理员持 `observations.manage_grants`。新的权利条款经受控 `register_grant` 入账，核对操作、受众、地域、对象、指标、字段、数据日期、生效和留存截止。演练用 F 自有范围，重授按新登记生效点核算连续性。撤回前 `GET admin/grants/<grant_id>/actions/` 获取产品当前 `version`，同路径 POST `action: "withdraw"`、`request_id`、`expected_version` 及 `reason_code`（`terms_ended`、`retention_withdrawn` 或 `rights_review`）。回读 `action_id`、`version` 和 `state: "withdrawn"`。

撤回生效后先对账受影响的现行查询、下钻、导出和历史导入操作，再对账物理清理。单独失去展示、导出或恢复许可时停止相应用途，仍有留存依据的数据按授权保留。留存权中断后，旧代次的暂存、受控副本和数据不能因重授恢复可用。到期按 PG 时钟和已登记条款处理，不能依赖 Worker 按时完成来保证断权。已到期的实际清理范围与未受影响的合法对照均须回读确认。

1. `GET admin/disposition-products/<product_id>/` 查看已到期待办、`error_code`、权利 `version` 和待办指纹 `basis`。
2. 同一 Session、同路径 POST `action: "prepare_disposal"`、`reason_code: "due_reconciliation"`、新 UUID `request_id`、`expected_version` 和原 `basis`。只有待办与权利快照一致时才获得 `operation_id` 和 `expires_at`，授权有效期 3 分钟。
3. 在该操作号对应的受控应用环境运行以下命令。收到完成回执后回读待办、数据库及文件清册，核对原范围物理移除与合法对照保留。命令在锁内复核具名主体、待办和权利版本。专用 Worker 路径只协调已登记待办，可在 `services` 隔离复验。

```sh
.venv/bin/python backend/manage.py s06_dispose --operation "$S06_DISPOSAL_OPERATION"
```

`precondition_conflict` 时复查待办、期限及权利版本并重新预演。介质不可达、文件仍有读占用或核销未完成时保留处置状态，查适用的错误码和任务收据，修复同一受控介质后再试。受控目录需支持 Linux `user.*` 扩展属性、文件锁和目录 `fsync`。旧清册缺少可信目录代次或卷离线时保留待办，重新挂回原介质后复验清理。`legacy_boundary_review` 待办须保留待证据复核。不要直接删除清册、伪造完成或重填权利期限。

## 分段备份与包外签认

备份操作者持 `accounts.manage_backups`，权利保管人由独立信任配置指定且具 `observations.manage_grants`。备份根 `S06_BACKUP_DIR` 与包外授权根 `S06_AUTHORITY_DIR` 由受控配置指定，应用对授权目录只有读取权。保管人独立持有原条款、离线私钥、可信锚点、主体映射及签发记录。把包外保管目录只读挂载给应用。`public.pem`、`trust.json`、`authority_id` 和 `subjects.json` 由受控配置提供，历史操作者映射还须与现行 PG 中的 `BackupSubject` 对账。每段按当前范围核 `backup` 和 `retain_normalized`，恢复再核 `restore`。原始字段默认不备份。例子中的站码、地理和日期均出自 F 专项。

1. 操作者 POST `admin/backup-products/<product_id>/segments/`。示例 JSON 为 `{"scope":{"geography":"F-city","object_code":"001","indicator":"CO","start":"2024-01-01","end":"2024-01-02"}}`。也支持布尔 `raw`。只有授权明确覆盖额外 `raw_field` 才可用 `true`。成功 `201` 返回分段 `operation_id` 和 `preparing`，此时文件仍不可取。
2. 保管人用独立 Session `GET admin/backup-authority/publish/<segment_id>/`。把范围、清册、末版本、链摘要、时间和操作号同原条款及包外记录对账。仅把已复核材料交给离线签发工具，在保管目录保留证明。材料的签认可用期限最长 2 分钟。应用收到签认后，仍须在线对照未回滚的权威 PG。
3. 原备份操作者在生效期内向 `admin/backup-segments/<segment_id>/publish/` POST `{}`。成功 `200` 且为 `available` 时核对分段清册、内容摘要、依赖和已登记副本。各段单独验权。发生留存或备份权中断时，相关准备件或旧段失效，相交段待核销。以仍连续合法的业务数据另行准备新段，受影响的旧段保持禁用。

逻辑段格式 `s06.logical.v2` 记录历史主体 token 与稳定 UUID。服务在写 `.partial` 前先提交卷代次、范围和清理待办。准备阶段限时五分钟，并受最早权利截止约束。清册写入失败后，按待办定位该段及原卷。发布和一次性读取在权威事务提交后还会复核包外证明与 PG 时刻，跨过有效期时收据转为 `withheld`，仍需核销的副本按原卷处理。发布确认提交后还需在现行来源/产品锁下重新核验签认，并给原文件写放行标记。若进程中断且标记缺失，恢复入口拒绝读取。盘点确认同卷、发布者已结束且仍无标记后，先持久登记 `blocked` 和到期待办，再删除并在原卷复核。删除后 PG 回滚时，待办仍可定位该段。一次性探针把现行来源/产品锁持有至回环 HTTP 正文写完。

以下命令在保管人环境签发已审材料，参数由其受控目录提供。演练脚本代建一次性 F 保管目录及密钥。保管材料、签名、恢复操作号和密钥不写入公开收据。

```sh
env PYTHONDONTWRITEBYTECODE=1 .venv/bin/python scripts/s06_restore_sign.py \
  --reviewed-material "$S06_REVIEWED_MATERIAL" \
  --custodian-root "$S06_CUSTODIAN_ROOT" \
  --offline-key "$S06_OFFLINE_KEY"
```

发布或恢复因证明过期、当前序号不符、断链、签名或依赖失配被拒绝时，先回读段状态和包外当前依据。仍合法的段需取得与本次操作对应的新材料及签认。失去留存或备份依据的旧段进入核销。临时件和孤儿由受控扫描依据 PG 清册处置，缺失或离线的存储须核验后才登记完成。用保管人获准的 `backup-authority` 响应和 `BackupSegment` 状态对账，待办及失败原因可回读 `admin/disposition-products/<product_id>/`。受控运维在任务自有环境补扫到期待办，核对受影响副本消失、合法兄弟段仍 `available` 且能独立通过恢复。已有混合包按整份适用的留存依据处置，合法部分可在授权仍有效时从现行数据另备独立段。

## 一次性隔离恢复

通过专项运行器复现完整链路。它为本次运行另外建立空目标库和低权限角色，绑定运行标记与目标 UUID，在启动迁移和读取前核验隔离边界。目标 schema 由 `bootstrap_target()` 完成准备，进入恢复命令时须保持业务表、账号和 Session 均为空。保管人私钥位于应用沙箱之外，公开材料以只读方式挂入。没有通用 DSN 参数和常驻恢复入口。

```sh
env PYTHONDONTWRITEBYTECODE=1 .venv/bin/python scripts/s06_restore_verify.py
```

1. 恢复操作者用独立 Session 向 `admin/backup-segments/<segment_id>/restore-intents/` POST `{"target":"<本次目标 UUID>"}`。`201` 返回短期 `operation_id` 和 `expires_at`。保持签发请求的 Session 有效。
2. 保管人 GET `admin/backup-authority/restore/<operation_id>/`，按本次操作、段、目标和 PG 当前状态复核并签发 `restore` 证明。可用性取操作、分段、现行权利与签认的最早截止。旧证明即使签名正确也不能替代本次材料。
3. 在已经守卫的演练环境，调用 `.venv/bin/python backend/manage.py s06_restore "$S06_RESTORE_OPERATION"`。命令按目标 UUID 及运行环境核验隔离库，校验具名角色、原 Session、当前权利、包外材料和依赖，只消耗一次意图。真实回环 HTTP 探针检查匿名拒绝、新 Session、一次读取和重复拒绝。输出脱敏对账及状态，不带逐条测值。
4. 放行前再次与权威 PG 对账，撤权先提交时拒绝读取。确认目标卷没有可取的业务行、账号和 Session，运行器销毁任务自有资源。读取、导入或最终核权失败时回滚目标数据。检查原意图是否已消费，若仍有恢复资格，则用空白目标和新意图重新签认。权威 PG 失联、现行证明不可确认、发现依赖不可映射或旧段已断权时拒绝。验收范围限合法业务子集和一次隔离读取。
