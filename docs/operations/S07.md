# S07 宿主启动与运维

在 Linux 或 WSL2 的仓库根目录使用 Python 3.13。先准备依赖和实例，再日常运行 `python main.py`。宿主入口只使用本机 PostgreSQL、专用 Redis 和回环 HTTP。S07 的离线演练用任务自有实例和 F 数据。

## 1. 准备独立实例

1. 运行 `uv sync --locked`，激活 `.venv`。在完全离线的机器上，准备阶段需已有锁定依赖和所用镜像。
2. 分配唯一实例名和属主为运行账号、权限为 `0700` 的 `AQ_HOST_ROOT`。给 PG 建立专用业务库和低权限库属主角色，提前准备项目所需的 `btree_gist`。用当前 PG 管理身份设置该业务库的 `airquality.s07_instance` 数据库默认值，内容等于实例名。优先用根目录内独立子目录的 Unix socket，也可使用独占的环回非默认端口。
3. 给该实例启动专用 Redis。在 socket 模式下关闭 TCP，socket 放根目录内的另一个子目录并限运行账号访问。环回 TCP 使用非默认端口和独立认证。仅在确认实例归属、Redis DB 0 为空后，写入字符串键 `airquality:s07:instance`，值为同一实例名。保留该键用于探活和 Beat 归属判断。Redis 停机后启动新的空实例时，确认旧发布者已退出再登记此键。
4. 预建普通 Beat 锁文件，放在 ext4、xfs 或 btrfs 上由保管账号控制的目录。Beat 运行账号需要读权限，文件及其目录项应由保管账号管理。也可给 Beat 单文件只读 bind mount。用 `stat -Lc '%d:%i:%u' <锁文件>` 取得设备号、inode、属主，前接 `/proc/sys/kernel/random/boot_id` 和冒号，得到登记值。PG 管理员给同一业务库设置 `airquality.beat_lock` 数据库默认值和 `airquality.beat_mode='host'`。仅在确认旧发布者和在途消息后登记或换代。其他模式见第 4 节。

### 容器提供基础设施

用 `compose.host-infra.yaml` 作为唯一 `-f` 文件，指定新项目名和该项目的专用 `--env-file`。先运行 `config --services`，预期只有 `db` 和 `redis`。再核对均为 `network_mode: none`、无发布端口、只挂自有 socket 目录和 `pgdata`、镜像摘要匹配。启动时只请求 `db redis`。宿主通过 Unix socket 使用这两个服务。

```sh
docker compose -p "$AQ_INFRA_PROJECT" --env-file "$AQ_INFRA_ENV" \
  -f compose.host-infra.yaml config --services
docker compose -p "$AQ_INFRA_PROJECT" --env-file "$AQ_INFRA_ENV" \
  -f compose.host-infra.yaml up -d --pull never db redis
```

专用 Compose 环境包含 `.env.example` 中的数据库配置，以及 `AQ_INSTANCE_ID`、`AQ_HOST_ROOT`、`AQ_HOST_UID` 和 `AQ_HOST_GID`。在权限为 `0700` 的自有根目录中预建 `pg` 和 `broker`。`pg` 需允许容器内 PostgreSQL 账号写 socket，同时赋予宿主账号访问权限。`broker` 属运行账号、权限 `0700`。核对容器项目标签后，按前述步骤登记 PG 和 Redis 标记。实例内 Redis 每次启动时重新确认标记。

## 2. 宿主配置与一次性准备

将以下配置保存到用户配置目录 `~/.config/air-quality-platform/backend.env`，也可设置 `AQ_HOST_CONFIG` 或传 `--env-file`。文件需属本账号、权限 `0600`，按原样写 `KEY=value`。示例路径和实例名均需替换，应用数据库口令和 Django 密钥要填本实例生成的值。

```dotenv
AQ_INSTANCE_ID=aq-demo-local
AQ_HOST_ROOT=/path/to/aq-demo-local
POSTGRES_DB=aq_demo
POSTGRES_USER=aq_demo_app
POSTGRES_PASSWORD=
POSTGRES_HOST=/path/to/aq-demo-local/pg
POSTGRES_PORT=5432
DJANGO_SECRET_KEY=
CELERY_BROKER_URL=redis+socket:///path/to/aq-demo-local/broker/redis.sock
AQ_BEAT_LOCK_FILE=/path/to/custodian/aq-demo/beat.lock
AQ_STATIC_ROOT=/path/to/aq-demo-local/staticfiles
WEB_PORT=8000
DJANGO_ALLOWED_HOSTS=127.0.0.1,localhost
COOKIE_SECURE=0
CNEMC_MODE=off
```

这里 Redis socket 的访问凭据是文件权限。TCP 时将 `CELERY_BROKER_URL` 设为 `redis://:<专用口令>@127.0.0.1:<专用端口>/0`，并把 PG 的 `POSTGRES_HOST` 和端口改为已核验的实例。`--env-file` 与 `AQ_HOST_CONFIG` 同时提供时需指向同一文件。若设置了 `XDG_CONFIG_HOME`，默认路径随之变化。终端中的同名身份配置需与文件一致。`WEB_PORT`、`DJANGO_ALLOWED_HOSTS` 和 `COOKIE_SECURE` 可显式覆盖。适用环境只保留本实例变量，清除代理、`PG*`、`DJANGO_SETTINGS_MODULE` 和连接覆盖。

用 `python main.py check` 复核当前可读状态。新空库报告 `migrations_pending_run_explicit_migrate` 后，在已核验的实例上，用同一虚拟环境及同一受控数据库变量完成一次性准备。导入变量时以配置数据处理，避免 shell 执行或打印配置。`AQ_STATIC_ROOT` 使用专属目录，`collectstatic` 生成 Admin 所需资源。

```sh
python backend/manage.py migrate --noinput
python backend/manage.py collectstatic --noinput
python main.py check
```

需要暂存时，为 `S02_STAGE_DIR` 挂载根目录下独立的私有 tmpfs，运行账号拥有 `0700`，挂载标志为 `rw,nosuid,nodev,noexec`，容量为 9 至 32 MiB。已有的 `StagedInput` 使用原卷代次，介质缺失时先核对持久义务。启用备份时分别配置该根目录下的 `S06_BACKUP_DIR` 和 `S06_AUTHORITY_DIR`，按照 S06 手册核对合法范围、原卷和包外现行依据。保管人私钥由保管方另行保存。

## 3. 启动、检查和退出

| 命令 | 行为 |
|---|---|
| `python main.py` | 前台运行正式 Web、Worker、Beat，Worker 就绪后才启动 Beat |
| `python main.py web` | 独立启动 Gunicorn，使用 1 个 `gthread` worker，线程数见交付配置 |
| `python main.py web --dev` | 启动 Django 开发服务器，关闭 reloader |
| `python main.py worker` | 依次运行 `s02_dispose_due`、`s03_reconcile_due`，成功后订阅 `s01.fixture`、`s02.history`、`s03.collection`，并发数 1 |
| `python main.py beat` | 用已登记的本机文件锁和独立 PG 会话锁启动 Beat |
| `python main.py check` | 核对配置、PG 归属、Broker、迁移和受控存储，PG 会话只读 |

`/health/ready/` 返回 200 表示 Web 能查询 PG，PG 不可用时返回 503。独立 Web 可在 Broker 未运行时继续提供读查询。使用授权 Session 查询 `/api/v1/admin/operations/health/`，核对 Redis 及 Worker 的目标队列、最近消费和 Beat 脉冲。启动器校验新 Beat 脉冲对应本次的发布标记与持锁 PG 会话。`/admin/login/` 引用的 CSS 由同源 `/static/admin/` 提供。配置和私有存储目录与静态根隔离。

前台用 `Ctrl-C` 或向启动器发 `SIGTERM`。启动器先停本次启动的 Beat，再 warm TERM Worker，最后停 Web，超时才强停本次进程组。已知子进程异常退出将使本次监督进程返回非零。监督器 SIGKILL 后，从 `AQ_HOST_ROOT/launch-<组件>.lock` 读取记载的 PID 和 Linux 启动时刻，结合 `/proc/<pid>/stat` 核实实际残留进程。核实归属后平滑退出该进程，核对组内进程均结束再重启。若涉及 Beat，还应按下一节核对在途发布和 PG 业务窗。

| 诊断 | 处理 |
|---|---|
| `missing_*`、`conflicting_*`、`unsupported_environment_*` | 核对专用配置、文件权限及终端覆盖 |
| `database_identity`、`broker_identity` | 核对库属主、登录角色、实例标记、socket 或环回端口，先确认实际服务归属 |
| `migrations_pending_run_explicit_migrate` | 在隔离实例明确执行迁移，核对叶节点再启动 |
| `staticfiles_missing_run_collectstatic`、`overlapping_private_and_static_storage` | 为实测代码重新归集静态文件，校验各路径独立 |
| `stage_storage_unavailable` | 按第 2 节核对 tmpfs 选项、容量、属主、原卷与代次 |
| `web_port_unavailable` | 检查本机监听地址和进程归属，选可用端口或平滑退出已确认的自有服务 |
| `worker_queue_mismatch` | 核对 `AQ_WORKER_NODE`、三队列订阅和当前 Broker 实例 |
| `s02_dispose_due_exited_*`、`s03_reconcile_due_exited_*` | 在已核验实例检查处置或恢复命令以及 PG 待办，处理完再启动 Worker |
| `beat_exited_*`、`beat_readiness_timeout` | 检查文件、挂载、PG 和 Redis 的登记标记以及原持锁者状态 |

排查只记录阶段、组件、PG/任务关联号和脱敏错误。配置文件、Session Cookie、数据库密码、原始资料与私有包保留在受控目录内。

## 4. Compose 与 Beat 切换

正式 Compose 由 `compose.yaml` 和 `compose.offline.yaml` 组成。基础配置继续支持开发 Web，日常宿主结构由 `main.py` 管理。Compose 将登记文件只读绑定到 `/run/aq-beat.lock`，通过 `AQ_INSTANCE_ID` 和 `AQ_BEAT_LOCK_SOURCE` 连接实例登记。仅核准单独 Compose 的实例设置 `airquality.beat_mode='compose'`，仅核准宿主和同账户直接 CLI 的实例设置 `host`。受支持的同机混用需先验证共享底层文件及两个方向的 `flock` 争用，再将数据库默认模式设为 `shared`。批准组合以 V03 实测收据为准。一次 A03 仍使用自身专用调度停用配置。

切换、原进程 SIGSTOP、原 PG 会话丢失或文件变更时，先核持锁进程和源实例。确认旧发布者退出，核对已发或状态不明的 task ID、Redis 入队和 PG 的 `job/scheduled_for` 业务窗。按原文件及实例登记重新启动唯一发布者。锁身份包含内核启动标识，宿主冷重启后需重新核对和登记。禁止通过更改 scheduler、换假锁文件或 Worker 内嵌 Beat 绕过排他。

从仓库根复验宿主 V02。该入口自行申请任务属主资源、验证 V01、运行仅 F/I 的矩阵并写当轮收据。

```sh
.venv/bin/python -B scripts/verify_s07_host.py startup
```

运行及清理结果位于本轮 `tmp/s07-evidence/<run>/V01/result.json` 和 `V02/startup.json`。在 A 环境核正式 Compose 的 Web 命令、镜像静态资源和对应服务收据。H 离线冷启按有效权利和专用收据判定，真实城市试运行在本轮继续 NO-GO。

## 5. 断网冷启与分组件恢复

先准备锁定依赖和镜像，再关闭外部路由、DNS 上游和代理。确认启动配置仍指向原实例的 PostgreSQL 卷。冷启期间保留数据卷和应用密钥，先启动 PostgreSQL 和 Redis，再启动应用。PostgreSQL 就绪且 Redis 尚未启动时，可单独运行 Web 并读取已有数据。Redis 恢复后，按实例原有配置核对 Broker 登记标记，再启动 Worker 和 Beat。操作前确认组件和卷的归属。

用原有 Session 和新登录 Session 分别读取已有数据，核对 `/health/ready/` 和管理员运行健康接口。PG 停机时 Web 就绪端点应返回 503。Redis 停机时 PG 查询应继续返回，运行健康接口应标出 Redis 不可用。停 Worker 或 Beat 后观察心跳自然过期，再重启并核对新脉冲和待办状态。PG 停机后确认旧 Beat 失锁退出。PG 恢复后启动 Beat，核对排程锁及本次恢复后产生的 Worker 和 Beat 心跳，再检查过期租约和新任务回执。

在仓库根运行 V14 的 F/I 复验。每条命令独立申请任务自有环境与数据卷，并校验 V01。证据记录在 `tmp/s07-evidence/<run>/V14/`。

```sh
.venv/bin/python -B scripts/verify_s07_host.py offline
.venv/bin/python -B scripts/verify_s07.py offline
```
